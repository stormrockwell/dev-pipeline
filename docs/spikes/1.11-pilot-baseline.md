# Task 1.11 phase one: pilot baseline for the zone scan and the floor

This report measures how often the deterministic floor blocks a change for a reason a reviewer would reject, on two pilot repos and on this repo. It is read-only. No code changed, and the pilots were only read. The tuning PRs in phase two should use the ranked proposals at the end.

## Method

The scan ran once per commit as `pipeline scan-zones --range <sha>^..<sha> --json` and `pipeline classify --range <sha>^..<sha> --json`, with the pilot as the working directory and `GIT_OPTIONAL_LOCKS=0` set. The CLI was `./cli/bin/pipeline` from `main` at `a50f800`, which does not yet hold PRs #20 and #21. No pilot has a `.pipeline/sensitive.yml`, so every scan used the built-in `wordpress` and `node` packs.

| Repo | Window | Notes |
|---|---|---|
| Media on Autopilot | the last 40 commits, first parent, no merges exist | Taken from the checked out branch `feature/self-hosted-cdn-multitenant`, which is the window the 0.6 spike used. Local `main` holds one commit and `origin/main` holds 12, so the default branch alone would give too small a sample. |
| MCP Server | 4 of 5 commits | `--range` cannot take the root commit, because it needs a parent, so `e9b76bf` (the initial push) could not be scored. The repo has only 5 commits, so the window is smaller than 40. |
| dev-pipeline | the last 15 squash commits on `main`, PRs #3 to #18 without #10 | All 15 scored. |

Judgments of each match are mine, made by reading the matched line and the surrounding diff. A match is true when a reviewer should look at it, a false positive when the matched text carries no risk, and debatable when a fair reviewer could go either way. A T3 commit is false-positive-only when every one of its matches is a false positive, and debatable-only when it has no true match but at least one debatable one.

The floor ran with `pipeline check --json` in APFS clones under the session scratchpad, with no installs. The Media on Autopilot clone was reset to `HEAD` for the second run so that the user's uncommitted changes would not count as baseline. Afterwards the pilots were unchanged: the Media on Autopilot index mtime and its 23 uncommitted entries are identical to before, and the MCP Server index predates this session.

## Other findings

- `--range` fails on a root commit with `"<empty tree>" is not a commit`. A first commit is then unscorable, and a new repo's first PR is exactly where a large unreviewed diff lands. Supporting a `--root` form, or diffing against the empty tree, would fix it.
- Neither pilot nor this repo has a `.pipeline/sensitive.yml`, so every number here comes from the packs alone. Repo-local path rules are the cheaper, stronger signal the strategy asks for.
- `.distignore` must not decide what counts as shipped. Both pilots exclude `/tests` and `/assets/test`, which are safe to treat as tests, but Media on Autopilot also excludes `/cloudflare` and `/bin`, and the Workers in `cloudflare/` are deployed code.

## Ranked tuning proposals

The proposals are ordered by false positives removed per unit of risk added. The column of counts is measured on the data above. None of them hides a change to shipped code, and each lists what it could hide and what keeps that covered. They all touch scan-zones config or packs, as #20 and #21 do, so they should land after those PRs.

| Rank | Proposal | Measured effect | Risk |
|---|---|---|---|
| 1 | Skip content signals in test files, keep path rules and the `secrets` zone | 125 of dev-pipeline's 153 false positives, 2 of 6 for Media on Autopilot, 27 of 95 tree matches | Low |
| 2 | Tree mode reads only files git would commit | 41 and 15 tree matches in git-ignored files, no per-change effect | None for committed code |
| 3 | Ignore an edited sink call whose target did not change | 3 of Media on Autopilot's 4 false-positive-only commits | Medium |
| 4 | Treat a comment-only edit to a migration as no path hit | 1 of Media on Autopilot's 4 false-positive-only commits | Low |
| 5 | Drop plain `child_process` import lines | 9 matches, no commit changes tier alone | Very low |
| 6 | Split the process spawn signal by risk | 12 debatable matches, 4 of dev-pipeline's 11 T3 commits | Medium |
| 7 | Narrow the `phpcs:ignore` pattern to security sniffs | 2 tree matches in Media on Autopilot | Very low |

### 1. Skip content signals in test files

Content signals would not run on files that match `**/test/**`, `**/tests/**`, `**/__tests__/**`, `*.test.*`, `*.spec.*` and `*Test.php`. Path rules still apply, so a test file under `.github/` or a manifest stays T3, and the `secrets` zone keeps scanning tests. Tests still classify as T2.

It could hide a vulnerable helper that lives in a test directory but ships, a test bootstrap that bypasses a security control (for example a constant that skips nonce checks), and a test file that ships by mistake. Three things keep that covered. The directory list is explicit and does not read `.distignore`, so `cloudflare/` and `bin/` stay scanned. A repo can narrow or extend the list in `sensitive.yml`, for instance a `test_paths` key, so a project with a shipped `tests/` directory opts out. And the floor keeps running gitleaks and semgrep on test files, and the strategy's mutation check still proves that security tests bite. A removed `permission_callback` test is not a signal today and is not made one.

A test that mentions `$_POST` in a string should also not count as the request data that triggers the write heuristic, which this proposal gives for free.

### 2. Read only the files git would commit in tree mode

Tree mode would list files with `git ls-files --cached --others --exclude-standard`, the same listing `check` already uses in `scope.ts`, and fall back to the directory walk outside a git repo. #20 skips `dist/` and `build/` by name, and this covers `.claude/`, `public/build`, `.next` and whatever else a repo ignores.

Ignored files are not part of any change, so no committed code is hidden. The residual risk is a repo that ships a generated directory it also ignores. That directory is rebuilt in CI per the strategy's "vendored and built code counts" rule, so the CI rebuild comparison owns it.

### 3. Ignore an edited sink call whose target is unchanged

For the non-literal sink signals (`fetch`, `exec`, `include`, `redirect`), an added line would not match when the same hunk removes a line with the same callee and first argument after whitespace normalization. This is the `fetch( originUrl.toString(), ... )` case, where only the options or the line wrapping changed. Authz, csrf, crypto, auth and data-loss signals keep matching on every added line.

It could hide a change to how an existing sink behaves, such as a new `redirect: 'follow'` option or a different method. Cover it three ways. Any change to the callee or to the first argument still fires. The `near` request-data signals still fire when `req.*` or `$_GET` reaches the call. And the review package lists the touched sink as information, so the security reviewer's zone call still reads it. The Media on Autopilot commit `991b1b5` shows the real cost: it would drop to T2 although it adds `isSignatureValid` and tenant resolution. That is why this proposal needs the repo-local rules in the next section first.

### 4. Treat a comment-only edit to a migration as no path hit

When every changed line in a `data-loss` path rule file is blank or a comment, the path rule would not raise the file. SQL comments are `--` lines and `/* */` blocks, with `/*!` and `/*+` excluded because MySQL executes them. Do not extend this to `guardrails` paths, because a comment in a workflow or in `CODEOWNERS` can carry a directive such as `nosemgrep`, `yamllint disable` or an owner change.

It could hide a comment that is really a directive, which the exclusions and the guardrails exemption cover. Migration order and filename still come from the path, and a renamed file is a rename, not an edit.

### 5. Drop plain `child_process` import lines

An `import` or `require` of `child_process` with no alias would stop matching, because the calls already match. Keep the line when it renames (`{ exec: run }`) or takes a member (`.exec`), since a later `run( cmd )` would not match. It removes noise only, and leaves the commit tier to the calls.

### 6. Split the process spawn signal by risk

The Node pack would treat these as the input zone: `exec` or `execSync` with a template or concatenated string, any call with `shell: true`, a non-literal command, a literal command that is a shell or interpreter (`sh`, `bash`, `cmd`, `node -e`), and installers (`npm install`, `composer install`). A `spawn`, `spawnSync` or `execFile` with a literal command, a literal argument array and no shell would stop matching. In the sample this clears 12 debatable matches and moves 4 of dev-pipeline's 11 T3 commits to T2.

It could hide argument injection through a variable array element (`git show ${spec}` with a leading dash) and a literal command that is itself dangerous. The listed exceptions cover the second case, and the first is covered by the request-data `near` signal and the security reviewer. For dev-pipeline in particular, `cli/src/commands/{guard,secrets,hooks,scan-zones,check}/**` hold guardrail logic, so those should become path rules in its own `sensitive.yml` before this lands, which is the strategy's move from content signals to paths.

### 7. Narrow the `phpcs:ignore` pattern

`phpcs:ignore.*WordPress\.(Security|DB)` would become `phpcs:ignore.*WordPress\.(Security|DB\.(PreparedSQL|RestrictedClasses|RestrictedFunctions))`. `WordPress.DB.SlowDBQuery` and `WordPress.DB.DirectDatabaseQuery` are performance and caching sniffs, so suppressing them is not a security decision. The remaining risk is a future security sniff added under `WordPress.DB`, which a review of the sniff list at each WPCS upgrade would catch.

### Coverage to add before or with the tuning

These are not false positive removals. They are the repo-local `sensitive.yml` rules that make proposals 1 and 3 safe, and each came from a miss above.

- **Media on Autopilot.** Path rules for `cloudflare/**/src/**` in `authz` and `crypto`, so Worker auth, signature validation and signing code is covered by path and not by content. A `near` signal for the Worker helpers `isAuthorized`, `isSignatureValid` and `crypto.subtle`. A signal for `crypto.getRandomValues`. A `secrets` signal for new `OPTION_*SECRET*` and `OPTION_*TOKEN*` constants in the settings sanitizer map.
- **MCP Server.** The `near: '\$input\b'` write signal for the abilities channel, as the 0.6 spike proposed, and a path rule for `src/Abilities/**`.
- **WordPress pack.** Add WebCrypto (`crypto.subtle`, `crypto.getRandomValues`) to the node `crypto` signals, since Cloudflare Workers and browsers use it and not the Node module.
- **dev-pipeline.** Path rules for the guardrail command directories listed above, and for the zone scanner's own rule source, so `packs.ts` is T3 by path and its 15 regex strings stop counting as content hits.

### Expected result of ranks 1, 3 and 4
