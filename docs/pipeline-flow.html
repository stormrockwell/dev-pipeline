Dev Pipeline Flow

Developers describe what they want in plain words, and a router picks the lightest route: answer, report, quick change, change, debug, new project or spike. This chart is the change route, the full flow. Scripts make the calls that must not fail, agents judge, and humans approve. The floor runs on every change, and the compounder feeds what went wrong back into the rules.

01

Intake

Orchestrator · OpusExplorer · Sonnet

A developer describes the work, with no command to remember. The router names the route in one line and only this route runs the full flow; /work stays as an optional shortcut. The orchestrator reads the repo profile, and an explorer writes what it finds to a notes file, so later agents start from pointers instead of pasted history. A quick triage decides whether this is a spike or real work, how much shaping it needs, and whether obvious zone words like login or payment call for a human from the start.

Produces notes file and triage

Shape

Orchestrator · Opus

The orchestrator drafts the tasks and the files each one owns, so risk can be judged per task instead of guessed from the request. Paperwork matches the size of the work.

03

Classify

RulesOrchestratorSecurity reviewer

A tier belongs to a task, not the plan. Agent reviews follow each task, and tasks are grouped into PRs by human review path, so a person only reviews what needs a person. Every pass can only raise the risk.

Per task, at planning

Rules on owned files and description › Orchestrator reads intent and can raise

Per commit, on the real diff

Rules on the hunks and their callers › Security reviewer tags zones

At merge

risk-gate recomputes in CI › Peer approvals

The orchestrator catches vague requests at planning, such as "add an export button", which means data exposure and authorization even when no file name says so. Only a peer reviewer, never the author, can lower a tier or remove a zone, so a developer who misses the risk cannot talk the pipeline out of it.

T0 Docs T1 Presentation T2 Logic T3 Sensitive Spike

04

Work order

Developer confirms

One screen lists the tasks, each task's tier, the gates beyond the defaults, the PR split and the estimated cost. In new projects and repos with a test suite, TDD is assumed and only appears when a task skips it. Only an existing codebase without a suite gets it as a question, with a recommendation. The developer replies "go" or edits a line. Autopilot skips this step below T3.

Task 1   CSV formatter              T2
Task 2   REST route, permissions    T3   security tests, full review
Task 3   Export button              T2   axe, a11y pass
PR A     task 2, zone, 1 peer approval
PR B     tasks 1 and 3, stacked on PR A, 1 approval
Plan     serial, each task builds on the last; about 14 runs

Produces approved tasks, gates and PR split

05

Build

Implementer · SonnetStop hook

Each task gets a fresh implementer in its own worktree, with its own test database and cloned dependencies. Tasks run one at a time by default, and only tasks with zero overlap in files, interfaces or state run in parallel. Tests come first at the seams agreed in the work order. Only an existing codebase without a test suite gets asked first, with TDD recommended for large or sensitive work. A Stop hook runs the fast checks before an implementer can report done.

Produces green commits per task

07

Finish

Docs agent · Haiku, SonnetAsks before push

The docs agent syncs versions and the changelog, then writes the PR body from the work order, the ledger and the diff, never from the chat. Every PR ends with an auditor list (which ran, which skipped and why), and findings fixed before the PR opened never appear, because human reading time is the bottleneck. The pipeline pushes the branch and opens a draft PR, and only humans merge. Secret scans check every commit being pushed, and on repos that have it, GitHub push protection blocks known secrets at the server, so sensitive data never leaves the laptop.

Zone PRrisk:high or risk:criticalT3 tasks with the component's whole security logic, a Human review required section and a review guide.
Standard PRrisk:mediumT2 tasks, plus T0 and T1 until they earn zero approvals.
Low-risk PRrisk:lowT0 and T1 tasks. Still a PR with the floor and agent review, and no human once revert rates earn it.

Independent PRs merge as soon as they pass. A PR that needs another stacks on it, so the peer reviewer of a zone PR reads only zone code.

Produces labeled draft PRs

08

Approve

Requester and reviewers

Humans approve on GitHub. Agents never fill a human slot, and an approval covers one commit.

risk:low
T0, T1. 1 approval, dropping to 0 once revert rates stay flat
risk:medium
T2. 1 approval
risk:high
T3. 1 peer approval
risk:critical
Designated paths. 2 peer approvals

A required risk-gate check enforces the label. It recomputes risk from the diff, so removing a label never lowers the bar, and it blocks merge until enough peers approve, because a ruleset cannot key approvals on a label.

A peer is any developer other than the author. The author never counts, bots never count, and only approvals of the latest commit count.

Produces merge

09

Record

Gate record

Gates run, gates skipped with reasons, findings and cost go into the PR as hidden JSON. A run log records every stage's timing, every dispatch's tokens and turns, every review round, every tool call and every wait on a human. The compounder reads both alongside human review comments, reverts and escaped bugs.

Produces evidence for the compounder

What each tier runs

The classifier picks the tier from the diff, never from the author. New projects always get a suite and TDD, and TDD is assumed wherever a suite exists. Only an existing codebase without a suite gets asked, with TDD recommended for large or sensitive work and against it for a few low-risk functions.

The floor

Runs on every change through hooks and CI. Nobody can skip it, and it costs almost nothing.

  • PHPCS with the WordPress security and prepared SQL sniffs
  • PHPStan, and Psalm taint analysis
  • Semgrep, and ESLint with no-unsanitized
  • Secret scanning with gitleaks and an entropy check, before every commit and every push
  • Checks for external scripts, iframes, form targets and URLs in templates and CSS
  • composer audit and npm audit
  • axe accessibility check against WCAG 2.2 AA

Human review zones

Code that always gets a human. It moves into its own PR labeled risk:high or risk:critical, while everything else still ships as a normal PR.

  • Authentication, sessions and cookies
  • Authorization and capability checks
  • Nonces and CSRF protection
  • Input reaching queries, uploads, shell calls or redirects
  • Browser sinks such as innerHTML
  • Third-party scripts, iframes, forms, fonts and CSS imports
  • New environment, credential or configuration files
  • Personal data being collected, logged or exported
  • Schema changes, bulk deletes and uninstall routines
  • Helpers that zone code calls, even harmless-looking ones
  • Cryptography, secrets and security suppressions
  • The guardrails: .github, .claude, .pipeline, linter configs and dependencies

What the compounder changes

It asks two questions of every run: what slipped through, and what slowed the pipeline down. Every lesson becomes a proposed change with an eval or a before and after measurement, and a human approves each one.

What slipped through

Mechanical mistake
A lint rule, sniff, Semgrep rule or hook
Judgment call
A line in the reviewer's REVIEW.md
Missed sensitive code
A rule in sensitive.yml
Wrong tier
A classifier rule change
Instruction with no effect
A deletion

What slowed it down

A stage that waits
Parallel work, a cached setup, or a timely notification
A loop that repeats
A sharper brief, or a check moved into the Stop hook
A repeated tool sequence
A script in the pipeline CLI, at zero tokens
A file every agent reads
A line in the notes or the brief
A role a cheaper model handles
A model change, proven in evals
An expensive model on mechanical work
